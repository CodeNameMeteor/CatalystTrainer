# CatalystTrainer — Full Code Review (October 2026)

**Scope:** the whole repository at `main` @ `52d608d` ("Merge branch 'main' …", 2026-09-25).
**Type:** inspection only. This report is the only change; no existing files were touched.
**Areas covered:** security, bugs and correctness, code quality, performance and accessibility.

---

## 0. How this review was done

- I read every first-party file line by line: `Injector/Injector.cpp`, `src/dllmain.cpp`, `src/Core/*`, `src/Game/*`, `src/Features/*`, `src/UI/*`, and every header under `include/Core`, `include/Game`, `include/Features` and `include/UI`. That's about 2,400 lines.
- I spot-checked the vendored third-party code (kiero 1.2.6, MinHook, Dear ImGui 1.83 WIP) only where our code relies on how it behaves, for example `kiero::shutdown()`, `kiero::bind()` and the ImGui Win32 WndProc handler.
- **Build check.** There is no MSVC toolchain in the review environment, so I ran each first-party translation unit through `x86_64-w64-mingw32-g++ -std=c++20 -fsyntax-only` with the repo's include paths. Some diagnostics come from MSVC-only syntax that MinGW doesn't accept (`__try/__except`), and I ignored those. The errors listed under **B-01** don't depend on the compiler: they are undeclared identifiers and missing members, so MSVC reports them too.
- I can't verify the game offsets and pointer chains without the game binary. Where a finding depends on what a game field actually means, it says so.

Severity scale: **Critical** means it blocks shipping or reliably breaks the core experience. **High** means a likely crash, memory corruption or a feature that silently fails. **Medium** means a real defect with narrower impact. **Low** covers hygiene, edge cases and docs. **Info** is advisory.

## 1. Executive summary

1. **`main` does not build.** Four translation units fail to compile because the headers and `.cpp` files have drifted apart (`Core::IsUnloadRequested`, `TrainerFeatures::Shutdown`, `m_NeedsTeleport`, `Addrs.camFwdX`). Whatever binaries were shipped were built from code that isn't in the repo. There's also no CI to catch this.
2. **Several features do something different from what the UI says:**
   - *Fast Loads* sets the game's time scale to 3000× on every tick, and switching it off never puts it back.
   - The *God Mode* checkbox does nothing.
   - *Bloom/Blur/Vignette* write 4-byte integers into what look like 1-byte fields, which overwrites neighbouring settings.
3. **Unloading is racy.** The DLL frees itself on a fixed 150 ms timer without waiting for its own logic thread or the WndProc to finish. It also leaves a lot of game state modified.
4. **The injector loads the DLL from the current working directory** and the README tells users to run it as Administrator. Together that's a classic DLL-planting setup. It also frees the remote path buffer after a timeout while `LoadLibraryW` may still be reading it.
5. **Thread-safety.** Three threads share all trainer state with no synchronisation: the game's window thread, the render/Present thread and the trainer's logic thread. That includes ImGui, which isn't thread-safe.
6. **Performance is not a concern.** Per-frame and per-tick costs are tiny. The one timing problem is correctness: the logic loop's `Sleep(16)` makes noclip speed depend on the system timer resolution.
7. **Accessibility gaps:** no UI scaling, no keyboard or gamepad navigation, hard-coded WASD/Space/Shift/Alt/C noclip controls, a default menu key (Insert) that many laptops don't have, and an injector console that closes itself 5 seconds after printing an error.

### Recommended order of work

1. Fix B-01 so the code builds, and add a Windows CI build job. Then fix the three feature bugs: B-02 (Fast Loads), B-03 (God Mode) and B-04 (visual-flag writes).
2. Make unloading safe (B-05) and make the injector load only from its own directory with least privilege (S-01, S-02, S-03).
3. Add a game-build check before any memory is written (S-04).
4. Tackle input handling (B-06, B-07, B-12) and the thread-safety model (B-15, B-16, Q-07).
5. Then the remaining Medium and Low items, accessibility, and docs.

## 3. Bugs and correctness (detail)

### B-01 — `main` does not compile · **Critical**

All of these come from header/implementation drift, and all of them fail on any compiler:

| File:line | Error |
|---|---|
| `src/dllmain.cpp:37` | `'IsUnloadRequested' is not a member of 'Core'`. It's defined in `src/Core/Hooks.cpp:283` but never declared in `include/Core/Hooks.hpp`. Introduced in `7097508`. |
| `src/dllmain.cpp:44` | `'TrainerFeatures' has no member named 'Shutdown'` |
| `src/Features/TrainerFeatures.cpp:158` | `no declaration matches 'void Features::TrainerFeatures::Shutdown()'` |
| `src/Features/TrainerFeatures.cpp:62,189` | `'m_NeedsTeleport' was not declared` (missing from `include/Features/TrainerFeatures.hpp`) |
| `src/Game/GameState.cpp:45,60-64` | `'Addresses' has no member named 'camFwdX'` (missing from `include/Game/GameState.hpp:42-51`). This has been broken since the very first code commit, `5cd0461`. |

**Impact:** nobody can build the trainer from source, so the README's "How To Compile" instructions don't work. The released DLL was built from code that isn't committed.

**Fix:**
- Declare `bool IsUnloadRequested();` in `Hooks.hpp`.
- Add `void Shutdown();` and `bool m_NeedsTeleport = false;` (ideally `std::atomic<bool>`, see Q-07) to `TrainerFeatures`.
- Add `uintptr_t camFwdX = 0;` to `GameState::Addresses`.
- Add a GitHub Actions `windows-latest` job running `cmake -B build -A x64 && cmake --build build --config Release`, so this can't happen again.

### B-02 — Fast Loads forces 3000× game speed and never turns off · **High**

`src/Features/TrainerFeatures.cpp:400-420`:

```cpp
bool fastLoads = false;                 // local, re-initialised every call
if (cfg.State.fastLoads && !fastLoads)  // always true while enabled
{   ... ResolvePtrChain(engine,{0x2c}) = 50000.0f;
    ... ResolvePtrChain(engine,{0x48}) = 3000.0f; }   // 0x48 is the time-scale field (see Menu.cpp:174, Shutdown)
else if (!cfg.State.fastLoads && fastLoads) // never true: fastLoads is always false here
```

- While Fast Loads is enabled, the time scale is overwritten to **3000** on every ~16 ms tick, during gameplay as well as during loads. It also overrides the "Game Time Scale" slider.
- When it's unchecked, the restore branch can't run, so the game **stays at 50000 / 3000** until the trainer unloads. `Shutdown()` restores `0x48` but never restores `0x2c`.
- `ProcessGodMode()` (`:208-224`) has the same local-flag bug. It's dead code today because the call is commented out, but it will break the moment someone turns it back on.

**Fix:** make the "applied" flag a member. Apply the change only while `game.IsLoading()` is true, and restore the previous values (read them before overwriting) when loading ends or the option is switched off. Restore `0x2c` in `Shutdown()` as well.

### B-03 — God Mode checkbox does nothing; god mode silently lost · **High**

- The menu checkbox (`src/UI/Menu.cpp:219`) only flips `cfg.State.godMode`. The only code that writes the `immortal` field is the hotkey path (`TrainerFeatures.cpp:44,50`), and the per-tick enforcer `ProcessGodMode()` is commented out (`:200`). Ticking the box changes the overlay tag to "God" but has no effect in game.
- With the hotkey, the write goes to whatever `Addrs.immortal` resolved to at that moment. If the chain wasn't resolved yet (main menu, loading) or the player object is rebuilt later (death, respawn, level load), the write is lost and never repeated. The UI keeps saying "God".

**Fix:** enforce state every tick, the same way noclip does. Keep a member `m_GodApplied`, write `1` while `godMode && HasPlayer()`, and write `0` once on transition to off. Remove the direct write from `HandleInput`.

### B-04 — Visual toggles write 4 bytes into 1-byte, adjacent fields · **High**

`src/UI/Menu.cpp:182,187,192` write `SafeWrite<int>` to `…+0x22B` (bloom), `…+0x228` (blur) and `…+0x239` (vignette).

- `0x22B` and `0x239` are not 4-byte aligned, and `0x228` and `0x22B` are only 3 bytes apart. These are almost certainly `bool`/byte flags in a Frostbite settings struct.
- Writing an `int` to `0x228` (blur) overwrites bytes `0x228-0x22B`, **including the bloom flag**. Writing to `0x22B` overwrites `0x22B-0x22E`, and writing to `0x239` overwrites `0x239-0x23C`. Each toggle zeroes or sets three neighbouring settings.
- This is the most likely explanation for the "Vignette (Use at own risk)" label.
- The checkboxes also start as `false` whatever the game's real state is, so the first click can set a flag to the value it already has.

**Fix:** use `SafeWrite<uint8_t>` (or `bool`) and read the current values when the tab first opens, so the checkboxes match the game.

### B-05 — Unload/eject is racy and incomplete · **High**

`src/Core/Hooks.cpp:68-111` runs on the Present thread when the user clicks *Unload*:

1. **Fixed 150 ms grace period.** A detached thread calls `FreeLibraryAndExitThread` after `Sleep(150)` (`:104-107`), but:
   - `MainThread` (`src/dllmain.cpp:37-45`) may still be inside `Tick()`. `TeleportToSaved()` alone sleeps 50 ms, and the Windows timer can stretch `Sleep(16)` to about 31 ms (P-01). It may also still be running `Shutdown()` or returning through DLL code when the image is unmapped, which crashes the game.
   - The game's window thread may be inside `HookedWndProc` (or about to call it with a cached pointer) when the module goes away.
   - **Fix:** keep the `MainThread` handle, have the eject thread `WaitForSingleObject` on it, and only free the module once no thread can be inside our code. Restore the WndProc on the window's own thread (for example by posting a private message and doing the restore inside `HookedWndProc`).
2. **Partial restore.** Input flags, `immortal`, time scale and movement properties are reset (`TrainerFeatures::Shutdown`). These are *not* reset:
   - Fast Loads `0x2c` (B-02)
   - bhop friction values if a bhop is armed (B-11)
   - visual flags (B-04)
   - time-of-day freeze value
   - a running noclip, which is restored only if `HasPlayer()` happens to be true.

   The comment at `Hooks.cpp:91` ("add reset movement properties to default") shows this was known.
3. **Leaks.** `pDevice` and `pContext` (`AddRef`'d at `:115-117`) are never released on unload. Neither are the MinHook trampolines, because `kiero::shutdown()` only disables hooks and never calls `MH_Uninitialize` or `MH_RemoveHook`. The leaks are small but grow if the trainer is injected and ejected repeatedly. The `CreateThread` handles in `dllmain.cpp:59` and `Hooks.cpp:104` are also never closed.
4. **Ordering.** `TrainerFeatures::Shutdown()` on the logic thread and the unload block on the Present thread both write the same input fields concurrently, so the end state depends on timing.

### B-06 — Hotkeys trigger on auto-repeat · **Medium**

`HookedWndProc` (`src/Core/Hooks.cpp:34-51`) acts on every `WM_KEYDOWN`/`WM_SYSKEYDOWN`. Windows repeats `WM_KEYDOWN` while a key is held, setting bit 30 of `lParam`. Holding the menu key or any toggle (God, Noclip, No Stumble) flips it on and off repeatedly, so the final state is effectively random.
**Fix:** ignore the message when `(lParam & (1 << 30)) != 0`.

### B-07 — Menu input blocking causes stuck keys and skips required cleanup · **Medium**

`src/Core/Hooks.cpp:53-61`: while the menu is open, *all* `WM_KEYFIRST..WM_KEYLAST` messages are swallowed, **including `WM_KEYUP`**. Two consequences:
- If a key is held when the menu opens (W to run, for example), the game never sees it released, and the player keeps running after the menu closes.
- `WM_INPUT` is swallowed without calling `DefWindowProc`. Microsoft's documentation says the application must call `DefWindowProc` for `WM_INPUT` so the system can clean up.

**Fix:** let key-up messages through, or synthesise releases when the menu opens. Call `DefWindowProc` for swallowed `WM_INPUT`. A cleaner approach is to rely on the game's own `inputEnabled`/`mouseEnabled` flags (which the trainer already writes) and stop filtering messages.

### B-08 — Many key bindings are lost on the next load · **Medium**

`ConfigManager::GetKeyName` (`src/Core/Config.cpp:44-69`) falls back to `GetKeyNameTextA`, and `ParseKeyName` can't read most of those names back:

| Bound key | Saved as | On load |
|---|---|---|
| `;` (VK_OEM_1) | `GodMode=;` | the value is cut off as a comment at `:156-158` → empty → binding reverts to default |
| `-`, `.`, `,`, `/`, `'`, `[` | `-`, `.`, … | `stoi` throws → 0 → reverts |
| Arrow keys | `Num 8` / `Num 4` (no extended bit passed to `GetKeyNameText`) | not in the map → reverts |
| Num Lock, Scroll Lock, Pause, etc. | localised names | reverts |

The UI also shows the wrong name for arrow keys ("Num 8").

**Fix:** persist anything that isn't in `s_NameToKeyMap` or A-Z/0-9 as hex (`0x%02X`), which `ParseKeyName` already accepts. Pass the extended-key bit (`1 << 24`) to `GetKeyNameText` for extended keys.

### B-09 — Noclip hotkey overwrites God Mode · **Medium**

`src/Features/TrainerFeatures.cpp:47-50` sets `cfg.State.godMode = cfg.State.noclip`. If God Mode was on before noclip, turning noclip *off* turns God Mode off as well. The menu's Noclip checkbox doesn't do this at all, so the hotkey and the checkbox behave differently.
**Fix:** track "god forced by noclip" separately, for example `bool effectiveGod = godMode || noclip`, and apply that every tick (see B-03).

### B-10 — Physics "restore" values are hard-coded, inconsistent and clobber user tuning · **Medium**

The same seven movement fields (`BhopFactorBase → 0x408 → 0x380 → 0x1C40..0x1C5C`) are "restored" to hard-coded constants in three places, and the constants don't agree:

| Field | MovementManager default (`MovementProperties.cpp:23-29`) | Teleport restore (`TrainerFeatures.cpp:149-155`) | Bhop restore (`:358-363`) |
|---|---|---|---|
| 0x1C40 Forward friction | 3.0 | 3.0 | **4.0** |
| 0x1C48 Strafe friction | 5.0 | 5.0 | **4.0** |
| 0x1C5C Max run speed | 7.2 | 7.2 | (not touched) |

- Every bhop permanently changes forward and strafe friction away from vanilla.
- Both teleport and bhop overwrite any values the user set in **Movement Tuning**, for example a custom Max Run Speed.
- **Teleport while noclip is on does nothing.** `ProcessNoclip` writes `m_NoclipPos` back over the player position on the next tick (`:293-295`) and never re-reads it.
- `TeleportToSaved` writes the camera and position three times in a row. That's copy-paste (`:126-144`), and the first copy writes `y - 3.0f`.
- `m_SavedVelocity` and `m_SavedCamPos` are calculated but never used (`:94,100`).

**Fix:**
- Read the current values before changing them and restore exactly those. Better still, ask `MovementManager` for the user's current values.
- After a teleport, re-sync `m_NoclipPos = m_SavedPos` if noclip is active.
- Remove the duplicated writes.

### B-11 — Bhop can stay armed indefinitely with friction zeroed · **Medium**

Pressing the bhop key (`TrainerFeatures.cpp:64-84`) immediately sets friction and deceleration to 0 and direction change to 1000. The restore only happens 50 ms *after the player leaves the ground* (`:337-364`). If the player never leaves the ground (stands still, gets into a cutscene, or the `onGroundStatus` chain doesn't resolve, since `SafeRead` defaults to `true`), the player stays on ice-like physics until something else rewrites those fields. There is also no way to cancel bhop from the UI.
**Fix:** add an arming timeout (for example 1-2 s) after which the original values are restored. Restore them in `Shutdown()` too.

### B-12 — Noclip responds to keys while the game is not focused · **Medium**

`ProcessNoclip` polls `GetAsyncKeyState` for W, A, S, D, Space, Shift, C, Alt and the speed keys (`TrainerFeatures.cpp:253-285`). That function reports the *global* keyboard state. If the user alt-tabs to a browser and types, the noclip player flies around and the speed changes in the background.
**Fix:** skip input when `GetForegroundWindow() != hGameWindow`. Better: keep key state updated from `HookedWndProc` messages.

### B-13 — Noclip modifier keys conflict · Low

`TrainerFeatures.cpp:267-284`:
- Shift sets `speedMultiplier = 1.5` **and** moves the player down (`:284`), so you can't fly level faster.
- The `if (speedMultiplier == …) … else …` toggling is effectively "Alt → 0.3, else Shift → 1.5", but it's written in a confusing way.
- Alt also triggers Windows menu-bar behaviour.

Use dedicated, rebindable keys (see A-04).

### B-14 — Injector robustness (Low/Medium, grouped)

`Injector/Injector.cpp`:

- **Exit code.** `main` returns `0` even when injection fails (`:328`), so scripts and launchers can't detect failure.
- **Auto-close.** It closes after `Sleep(5000)` (`:327`) on failure as well as success, so users have 5 seconds to read the error (see A-07).
- **Unresponsive window.** After 10 failed responsiveness checks it goes ahead and injects into a window that's still hung, without saying so (`:276-301`).
- **Window-title heuristics** (`:82-106`). If the game title is localised or changes in a patch, the injector loops forever printing nothing after "Waiting for game window". The `"EA"` substring filter is case-sensitive and very broad. Use a timeout with a message, or match the window *class*.
- **Process lookup.** `GetProcessIdByName` returns the first match. With two instances (or a leftover zombie) it may pick the wrong PID.
- **Module handle truncation.** `GetExitCodeThread` returns 32 bits, so the 64-bit `HMODULE` is truncated. The printed address (`:184`) is wrong, and the `exitCode == 0` success test (`:178`) is technically unreliable. Use `EnumProcessModulesEx` or `GetModuleHandle` via a snapshot to confirm the load.
- **Non-ASCII paths.** `std::wcout` without `_setmode(_fileno(stdout), _O_U16TEXT)` puts the stream into a failed state on the first non-ASCII character, for example a Unicode user name in the DLL path. After that, all later output disappears.
- **Path length.** `GetCurrentDirectoryW` and `MAX_PATH`: the return value is unchecked and long paths get truncated.

### B-15 — ImGui is used from two threads · **Medium**

- `ImGui_ImplWin32_WndProcHandler` runs on the **game's window thread** (`Hooks.cpp:55`), while `NewFrame`, `Render` and `DestroyContext` run on the **Present thread**. Frostbite renders on a dedicated thread, so these are normally different threads.
- Dear ImGui is explicitly not thread-safe. In 1.83 the WndProc handler writes `io.MouseDown`, `io.KeysDown`, `io.MouseWheel` and pushes to `io.InputQueueCharacters`, an `ImVector` that can reallocate, while `NewFrame` reads them.
- Worse, the re-init path (`:170-173`) calls `ImGui::DestroyContext()` while the window thread may be in the middle of the handler, which is a use-after-free.

**Fix:** have `HookedWndProc` copy the relevant messages into a small lock-protected queue, and replay them into ImGui on the Present thread before `NewFrame`. Or guard both sides with one mutex (simple, and contention is negligible).

### B-16 — `oWndProc` is cleared while the window thread may use it · **Medium**

The re-init path (`Hooks.cpp:192-193`) and the unload path (`:79-83`) restore the WndProc and then set `oWndProc = nullptr` **from the Present thread**. A message already being handled on the window thread then reaches `CallWindowProc(nullptr, …)` (`:63`) and is dropped. That message could be `WM_SIZE`, `WM_ACTIVATE`, `WM_CLOSE` and so on.

Between re-init and the next successful Present there's a gap where the trainer has no WndProc at all, so hotkeys don't work. If another overlay (Steam, Discord, RivaTuner) subclassed the window after us, restoring with `SetWindowLongPtr` removes it from the chain.
**Fix:** never null `oWndProc` while the hook might still be called. Keep the hook installed across device re-inits; only ImGui needs re-initialising.

### B-17 — Unchecked D3D calls in first-time init · Low

`Hooks.cpp:118-125`: if `GetBuffer` fails, `pBackBuffer` is null and `pBackBuffer->Release()` crashes. If `CreateRenderTargetView` fails, the code continues with `pRenderTarget == nullptr`. That case is handled later, but nothing is logged. `GetDesc` failure leaves `hGameWindow` uninitialised.

### B-18 — Hook installation failures are ignored · Low

`InitializeHooks` (`Hooks.cpp:262-271`) returns `true` as soon as `kiero::init` succeeds, even if `kiero::bind` fails (for example because another overlay already patched `Present` in a way MinHook can't handle). The trainer then runs its logic thread with no UI and no way to unload.
**Fix:** check both `bind` results, and log the problem (see Q-09).

### B-19 — Time-of-day controls drop the day counter · Low (needs game confirmation)

`Menu.cpp:147-169` normalises the raw value with `fmod(…, 86400)`, then writes back `hours * 3600` (slider) or the normalised value (freeze). If the game stores *elapsed* seconds, with days accumulating as the commit message "try to fix timeofday" suggests, each write resets the elapsed days. That could affect anything that depends on elapsed time.
**Fix:** write `raw - normalized + hours * 3600` to keep the day part.

### B-20 — README and code disagree · Low

- **Menu key.** The README says `M` toggles the menu (`README.md:22`), but the default is `VK_INSERT` (`include/Core/Config.hpp:9`).
- **Config file name and location.** The README says settings save to "`config.ini` in the game's directory" (`README.md:19`). The code writes `trainer_config.ini` **next to the DLL** (`src/Core/Config.cpp:110`), and the UI buttons also say "config.ini" (`Menu.cpp:257,264`).
- **What gets saved.** The README says "your settings will automatically save". Only 4 settings are saved (`Config.cpp:222-226`); toggles such as no-stumble, wall cheats and time scale are not. The keybinds are saved.

### B-21 — Default value mismatch for "Second WR Time" · Low

`MovementProperties.cpp:54` resets it to `64.0f`, but the header initialises it to `80.0f` (`MovementProperties.hpp:93`, matching "First WR Time" at 80). One of them is wrong, so "Reset All to Default" may write a non-vanilla value.

### B-22 — Inconsistent noclip speed limits · Low

The slider range is 0.1-5.0 (`Menu.cpp:225`), the hotkeys clamp to 0.1-10.0 (`TrainerFeatures.cpp:255-258`), and the config value isn't clamped at all (`Config.cpp:180`, which accepts `nan`, `inf` and negative values).

### B-23 — Movement tuning writes partial input to the game · Low

`ImGui::InputFloat` returns `true` on every edit (`MovementProperties.cpp:110`). Typing `0.5` writes `0`, then `0.`, then `0.5` to the game, and any value (`-1e30`, `inf`) is accepted. Use `ImGuiInputTextFlags_EnterReturnsTrue` or `IsItemDeactivatedAfterEdit()`, and clamp each property to a sensible range.

### B-24 — `FindPattern` defects (currently dead code) · Low

`include/Core/Memory.hpp:107-162`:
- A pattern containing any non-hex, non-`?` character (for example `"48 GG"`) makes `strtoul` consume nothing. That's an **infinite loop** that keeps pushing to `bytes` until memory runs out.
- `scanLen = end - start - patternSize` underflows if the pattern is longer than the image.
- `i < scanLen` skips the last valid position (off by one).
- It scans the whole image, including non-readable regions, with no SEH guard.

It isn't called anywhere today, but it's the natural fix for S-04, so fix it before using it.

### B-25 — Fragile includes / non-portable constructs · Low

- `#include <cstring>` **inside `class Memory`** (`Memory.hpp:36`). This only compiles because `<vector>`/`<algorithm>` already pulled `<cstring>` in through MSVC's internal headers, so the include guard turns it into a no-op. On MinGW it breaks the build. Move it to the top of the file.
- `Menu.cpp:149` uses `fmod` without including `<cmath>`, relying on transitive includes.
- `Hooks.cpp:266-267` pass function pointers where `void*` is expected (an MSVC extension). Add `reinterpret_cast<void*>`.

### B-26 — Conflicting bindings are allowed · Low

Nothing stops the same key being bound to two actions. The menu key always wins, so the other action can never fire. Binding to W, A, S, D, Space, Shift or C conflicts with noclip movement, and Escape can't be bound or cleared. Warn about duplicates in the Settings tab.

### B-27 — Unload path assumes an ImGui context · Low

`Hooks.cpp:76` calls `ImGui::GetIO()` before checking `bInitialized` (`:92`). If unload is requested during the re-init gap described in B-16, there's no context and this is a null dereference. It's rare, but trivial to guard.

## 4. Security (detail)

> Threat model: this is a local, single-user game trainer. The main risks are (a) the injector being tricked into loading the wrong code, possibly with elevated rights, (b) the trainer corrupting game memory and crashing the game or the user's save, and (c) harm to the user, such as leaderboard bans. There is no network code and no untrusted remote input in the trainer itself.

### S-01 — DLL planting via the current working directory · **Medium**

`Injector/Injector.cpp:200-220` builds the DLL path from `GetCurrentDirectoryW`, then falls back to `.\Release\MEC_Trainer.dll`. The current directory is whatever the launching shell, shortcut or file manager decided, not where `MEC_Injector.exe` lives. So:

- Starting the injector from a shortcut or terminal in another folder (Downloads, for example) loads *that folder's* `MEC_Trainer.dll`. Any DLL with that name gets mapped into the game.
- `README.md:13` tells users to "Run as Administrator if necessary", and the injector enables `SeDebugPrivilege`. An elevated process loading a DLL from a user-writable, attacker-influenced path is a textbook DLL-planting / privilege-boundary problem.

**Fix:**
- Resolve the DLL path from `GetModuleFileNameW(nullptr, …)`, which is the injector's own directory, and drop the `Release\` fallback, or limit it to debug builds.
- Optionally verify a hash or Authenticode signature of the DLL before injecting.
- Remove the "Run as Administrator" advice. The game runs unelevated under the EA app, so the injector doesn't need elevation. If `OpenProcess` fails with `ERROR_ACCESS_DENIED`, the more likely cause is the game itself running elevated, and the message should say that.

### S-02 — More privilege than needed · Low

- `EnableDebugPrivilege()` (`:9-31,195`) isn't needed to open a same-user, same-integrity process. Its return value is ignored, and `AdjustTokenPrivileges` returns success even when it sets `ERROR_NOT_ALL_ASSIGNED`.
- `OpenProcess(PROCESS_ALL_ACCESS…)` (`:121`) asks for far more than injection needs.

**Fix:** request `PROCESS_CREATE_THREAD | PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_VM_OPERATION | PROCESS_VM_WRITE | PROCESS_VM_READ`, and drop the debug privilege.

### S-03 — Remote buffer freed while `LoadLibraryW` may still use it · **Medium**

`Injector.cpp:169-185`: `WaitForSingleObject(hThread, 8000)` doesn't check its return value.

- If the game is slow (a first-run shader cache, Denuvo checks, antivirus scanning the DLL) and the wait times out, the code still calls `VirtualFreeEx` on the path buffer while the remote `LoadLibraryW` may be reading it. At best the load fails; at worst it reads freed or reused memory in the game.
- On timeout, `GetExitCodeThread` returns `STILL_ACTIVE` (259), which is non-zero, so the injector prints **"INJECTION SUCCESSFUL"**.

**Fix:** wait with `INFINITE` (or a long timeout) and treat `WAIT_TIMEOUT` as "unknown — not freeing the buffer". Check the exit code against `STILL_ACTIVE`.

### S-04 — No game-version check before writing memory · **Medium**

Every address in `include/Game/GameOffsets.hpp` is a hard-coded RVA for one specific build of `MirrorsEdgeCatalyst.exe`. On any other build (Steam vs EA app, a future patch, a different region or DRM wrapper):

- the pointer chains resolve to *valid but wrong* addresses, and `SafeWrite` happily writes floats and ints into unrelated heap objects;
- the range check in `IsValidAddress` and the SEH guard only catch *unmapped* addresses, not *wrong* ones;
- the result is silent memory corruption: crashes minutes later, broken saves or odd physics.

**Fix:** at startup, verify the build (PE `TimeDateStamp`, `SizeOfImage`, or a hash of `.text`) against the known value, and refuse to enable memory features on a mismatch, with a message in the menu. Longer term, find the roots with signatures (`FindPattern` + `ResolveRelativeAddress` already exist but are unused; fix B-24 first).

### S-05 — SEH handler catches everything · Low

`SafeRead`/`SafeWrite` use `__except (EXCEPTION_EXECUTE_HANDLER)` (`Memory.hpp:51,69`). That also swallows `STATUS_GUARD_PAGE_VIOLATION`. If a stale pointer lands on another thread's stack guard page, the guard is consumed, and that thread can later crash instead of growing its stack. It also hides real bugs in the trainer.
**Fix:** filter with `GetExceptionCode() == EXCEPTION_ACCESS_VIOLATION ? EXCEPTION_EXECUTE_HANDLER : EXCEPTION_CONTINUE_SEARCH`, and/or check the address with `VirtualQuery` (it must be committed, not `PAGE_GUARD`, and readable/writable) before touching it.

### S-06 — Config input not range-checked · Low

- `ParseKeyName` accepts any integer (`Config.cpp:89-92`), for example `GodMode=99999` or `-5`. Keep VK codes to 1-254.
- `NoclipSpeed` accepts NaN and inf (B-22). A NaN speed writes NaN into the player position, which can crash physics or corrupt the save.

Note that the parser itself is robust: there are no buffer overflows and every parse is wrapped in `try/catch`.

### S-07 — Fair play / user risk · Info

Catalyst has online features: leaderboards, time trials and user-generated "Beat" challenges (the unused `tpBeatLE` setting suggests these are being considered). Nothing stops trainer features while those are active, so users may submit cheated times and risk account action.
**Suggestion:** show a clear warning in the menu. Better, detect online/time-trial mode and disable features that affect movement or timing.

### S-08 — Distribution hygiene · Info

- Releases aren't signed and no checksums are published, so users can't tell a genuine `MEC_Trainer.dll` from a trojaned re-upload. That's a common route for malware in the trainer community.
- Commit `29e69d1` removed `CatalystTrainer.dll` and `LauncherConsole.exe`, but they're still in git history (about 530 KB). That's harmless, but anyone cloning gets unaudited binaries.
- There's no `LICENSE` file, and the vendored ImGui (MIT), MinHook (BSD-2-Clause) and kiero (MIT) require their copyright notices to ship with binary releases. Add a `THIRD_PARTY_NOTICES` file.

## 6. Performance

Overall the runtime cost is negligible. One item (P-01) is really a correctness problem with timing.

| ID | Finding | Impact | Suggestion |
|---|---|---|---|
| P-01 | The logic loop uses `Sleep(16)` (`dllmain.cpp:41`). At the default 15.625 ms Windows timer resolution, `Sleep(16)` usually sleeps **about 31 ms**, so the loop runs at about 32 Hz, not 60. Noclip moves a fixed amount per tick, so **noclip speed depends on the system timer resolution**, which changes depending on whether the game or another app called `timeBeginPeriod`. Position writes at 32 Hz against a 60-200 FPS game also make the game's physics pull the player back between writes (jitter). | Medium (feel) | Scale by elapsed time (`QueryPerformanceCounter`). | P-02 | `GameState::Update` resolves about 20 pointer chains every tick, each building a heap-allocated `std::vector` from an initializer list. `RenderImGuiCategory`, `TeleportToSaved` and bhop do the same per widget or per call. That's roughly 1-2k small allocations per second. | Negligible | Take `std::span<const unsigned>` / `std::initializer_list`, or use `static constexpr std::array` chains. |
| P-03 | The `GetTickCount() - last < 3` throttle in `GameState::Update` (`:17`) does nothing: `GetTickCount` has about 16 ms resolution and the caller already sleeps 16 ms. | None | Remove it. |
| P-04 | Per frame, `HookedPresent` calls `GetDevice` and `Release` just to detect device changes. The overlay builds a `std::vector` and `std::string`. The Settings tab calls `GetKeyName` 9 times per frame, which does a linear scan of an `unordered_map` plus `MapVirtualKey`/`GetKeyNameText` calls. | Negligible | Cache key names when bindings change. Compare `pSwapChain` only, and check the device on `ResizeBuffers` instead. |
| P-05 | `imgui_demo.cpp` (about 8k lines) is compiled into the DLL. | Binary size | `#define IMGUI_DISABLE_DEMO_WINDOWS` or exclude the file. |
| P-06 | `FindPattern` (unused) is a naive O(n·m) scan over the whole image. | Future | Scan only executable sections, and use `memchr` on the first non-wildcard byte. |

## 8. Positive notes

- The memory access helpers are defensive: range checks plus SEH, and pointer chains are re-resolved every tick instead of being cached forever.
- The config parser is careful: trimming, case-insensitivity, comment stripping, `try/catch` around every numeric parse, and defaults written on first run.
- Fullscreen and device-change handling in the Present hook (`90fa18f`) is the right idea; it only needs the thread-safety fixes in B-15 and B-16.
- The injector handles the EA-app splash/activation windows and process restarts sensibly, and cleans up remote allocations on every *failure* path. Only the timeout path is wrong.
- The static CRT (`/MT`) and the x64-only CMake guard are good choices for a drop-in DLL.
